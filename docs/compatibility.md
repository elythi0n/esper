# What talks to what

Two Esper installations at different releases still have to reach each other,
so the release number and the wire protocol version are separate things and
change for separate reasons.

## The two numbers

| | Where it lives | What it means |
|---|---|---|
| **Release version** | `VERSION`, and `esper version` | Which build this is. Semantic versioning. |
| **Protocol version** | `esper_proto::PROTOCOL_VERSION`, mirrored in `internal/proto` | What goes on the wire. Currently **1**. |

A release may change without the protocol changing, and usually does. The
protocol changing is a much larger event, described below.

## The protocol version must match exactly

It is not negotiated. Two peers whose `PROTOCOL_VERSION` differs close the
connection with `PROTOCOL_VERSION_MISMATCH` (reason code 100), naming both
versions, and the person is told which end to upgrade.

**This is deliberate, and the alternative is worse.** A protocol that
negotiates downward has to keep every older behaviour reachable, and every one
of those is a path an attacker can ask for by name — the version-downgrade
attack is a standing item in every protocol that has ever allowed it. Esper
would be choosing, in advance, to keep its own oldest code paths available to
whoever asks. A clean refusal that says what to upgrade is a worse afternoon
and a much better decade.

The ALPN identifier carries the same number (`esper/1`), so a mismatch is
refused during the TLS handshake where the versions differ that early, rather
than after a connection exists.

## Features are negotiated; the protocol is not

Within one protocol version, what a session can do is the **intersection of
what both peers advertise** — `Hello.caps`, intersected, sorted, deduplicated.
That is what lets a release add a capability without becoming incompatible
with the release before it: an older peer simply does not offer it, and the
intersection does not contain it.

So the rule for adding something to the protocol is:

- **A new capability, advertised in `caps`** — no protocol bump. The other end
  not having it is an ordinary outcome, not an error.
- **A change to an existing message, or to what a peer must do with one** —
  protocol bump. There is no way for the far end to detect this and no
  intersection that describes it.

A capability that is not really optional — one where a peer that lacks it
cannot complete a session that used to work — is a protocol change wearing a
capability's clothes, and it gets a bump.

## What a protocol bump costs

Every peer must be upgraded before any of them can connect again. There is no
partial rollout and no mixed fleet. For a product people install on machines
they cannot easily reach, that is expensive enough to be worth avoiding, which
is the point of the capability mechanism above.

When it does happen:

- The release notes lead with it, in those words.
- The reason code and its message are what people will actually see, so they
  name both versions.
- The old version's `ALPN` stops being offered, so an old peer fails at the
  handshake with a clear reason rather than midway through a session.

## Two implementations, one protocol

Esper is a Rust engine and a Go control plane, and both of them name the same
things on the wire. That is two chances to drift, so it is checked rather than
maintained by attention: `make check-vocabularies` compares the permissions,
the reason codes, the fingerprint wordlist and the domain separators between
the two, and CBOR fixtures generated by one are decoded by the other.

What that does **not** give is an independent reading of the specification —
two halves of one project are not two implementations. See the open risk about
a third-party implementation in the project's own risk list.

## Support window

Not yet decided, and saying so is more useful than inventing one. Esper is
pre-1.0 and has never been released; a support window claimed before the first
release would be a promise made by nobody to nobody. It belongs in this
document before 1.0.
